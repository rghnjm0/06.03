### №12. `routes/auth.py` → `register()` — генерация `ID_Клиента` через `COUNT(*)` даёт коллизии

```python
cursor.execute("SELECT COUNT(*) FROM Клиенты")
count = cursor.fetchone()[0] + 1
client_id = f"CL{count:03d}"
```

**Проблема:** если из таблицы когда-либо удалят хотя бы одну запись, `COUNT(*)` уменьшится, и новый ID совпадёт с уже существующим. `UNIQUE`-констрейнт отклонит вставку, транзакция откатится, а пользователь увидит «Не удалось завершить регистрацию».

В `admin.py` для той же задачи уже есть правильный инструмент — `utils.next_id()`. Здесь его забыли применить.

**Исправление:**
```python
from utils import next_id
...
client_id = next_id(conn, 'Клиенты', 'CL', 'ID_Клиента')
```

### №13. `routes/auth.py` → `register()` — соединение закрывается без отката транзакции

```python
conn.execute('BEGIN IMMEDIATE')
cursor.execute("SELECT ID_Клиента FROM Клиенты WHERE Телефон = ?", (phone,))
if cursor.fetchone():
    flash('Клиент с таким телефоном уже зарегистрирован', 'danger')
    conn.close()      # ← транзакция BEGIN IMMEDIATE всё ещё открыта
    return render_template('register.html')
```

SQLite при `close()` неявно откатывает транзакцию, поэтому порчи данных не будет, но это плохая практика: в пуле соединений или при переходе на другую СУБД приведёт к зависшим блокировкам. Также `except` не делает `conn.rollback()`.

**Исправление:**
```python
if cursor.fetchone():
    conn.rollback()
    conn.close()
    flash('Клиент с таким телефоном уже зарегистрирован', 'danger')
    return render_template('register.html')
```

И в `except`:
```python
except Exception:
    try: conn.rollback()
    except Exception: pass
    finally: conn.close()
    ...
```

### №14. `routes/payments.py` → `create_payment()` — можно оплатить отменённую бронь

```python
booking = conn.execute("""
    SELECT b.*, n.Номер_Комнаты
    FROM Бронирования b
    JOIN Номера n ON n.ID_Номера=b.ID_Номера
    WHERE b.ID_Бронирования=? AND b.ID_Клиента=?
""", (booking_id, session.get("client_id"))).fetchone()
```

**Нет проверки `b.Статус NOT IN ('Отменено','Завершено')`.** Если гость откроет страницу подтверждения старой отменённой брони и нажмёт «Оплатить», платёж пройдёт, счёт пометится оплаченным, но бронь отменена. В финансовой отчётности появятся «оплаченные отменённые» брони.

**Исправление:**
```python
booking = conn.execute("""
    SELECT b.*, n.Номер_Комнаты
    FROM Бронирования b
    JOIN Номера n ON n.ID_Номера=b.ID_Номера
    WHERE b.ID_Бронирования=? AND b.ID_Клиента=?
      AND b.Статус NOT IN ('Отменено', 'Завершено')
""", (booking_id, session.get("client_id"))).fetchone()
```

### №16. `routes/admin.py` → `admin_booking_add()` — нет серверной валидации `client_id` и `room_id`

```python
client_id = request.form.get('client_id','')
room_id = request.form.get('room_id','')
...
conn.execute("""INSERT INTO Бронирования(...) VALUES(?,?,?,...)""",
    (booking_id, client_id, room_id, ...))
```

Проверяется только `room_id`:
```python
room = conn.execute('SELECT * FROM Номера WHERE ID_Номера=?',(room_id,)).fetchone()
if not room: raise ValueError('Номер не найден.')
```

**`client_id` не проверяется вообще.** Если отправить POST напрямую с пустым `client_id`, SQLite выбросит `FOREIGN KEY constraint failed`, пользователь увидит «Внутренняя ошибка». Нужно:

```python
client = conn.execute('SELECT 1 FROM Клиенты WHERE ID_Клиента=?', (client_id,)).fetchone()
if not client:
    raise ValueError('Гость не найден.')
```

### №4. `routes/features.py` → `profile_edit()` — нет проверки уникальности телефона

```python
conn.execute("UPDATE Клиенты SET ... Телефон=? ... WHERE ID_Клиента=?", (..., phone, session['client_id']))
conn.execute("UPDATE Пользователи SET Логин=? WHERE ID_Клиента=?", (phone, session['client_id']))
```

Свободный гость может занять телефон другого клиента — сработает `UNIQUE`, транзакция откатится, но пользователь получит общее «Внутренняя ошибка». В `admin_client_edit` такая проверка есть, здесь её нет.

**Исправление:**
```python
duplicate = conn.execute(
    "SELECT 1 FROM Клиенты WHERE Телефон=? AND ID_Клиента<>?",
    (phone, session['client_id'])
).fetchone()
if duplicate:
    raise ValueError('Этот телефон уже используется.')
```

### №5. `routes/admin.py` → `admin_dashboard()` — «К оплате» может быть отрицательным

```python
revenue = ... WHERE b.Статус!='Отменено'
paid    = ... без фильтра по статусу
unpaid  = revenue - paid
```

Если оплаченный счёт относился к брони, которая позже была отменена, `paid > revenue`, и `unpaid` станет отрицательным. Карточка «К оплате» покажет бессмыслицу.

**Исправление:**
```python
paid = conn.execute("""
    SELECT COALESCE(SUM(s.Сумма_проживание),0)
    FROM Счета s JOIN Бронирования b ON b.ID_Бронирования = s.ID_Бронирования
    WHERE s.Оплачено=1 AND b.Статус != 'Отменено'
""").fetchone()[0]
```

### №8. `utils.py` → `sync_room_statuses()` — неявная зависимость от миграции

```python
conn.execute("UPDATE Номера SET Статус = 'Свободен' WHERE COALESCE(Статус_обслуживания,'') = ''")
```

Колонка `Статус_обслуживания` создаётся в `features.ensure_features_schema()`. Сейчас порядок в `app.py` корректный, но если кто-то вызовет `sync_room_statuses()` раньше (например, в CLI-скрипте), получит `OperationalError`. Стоит добавить проверку:

```python
cols = [r['name'] for r in conn.execute("PRAGMA table_info(Номера)").fetchall()]
if 'Статус_обслуживания' in cols:
    conn.execute("UPDATE Номера SET Статус='Свободен' WHERE COALESCE(Статус_обслуживания,'')=''")
else:
    conn.execute("UPDATE Номера SET Статус='Свободен'")
```

### №21. `utils.py` → `next_id()` — потенциальная гонка при отсутствии `BEGIN IMMEDIATE`

```python
rows = conn.execute(f"SELECT {field} FROM {table} WHERE {field} LIKE ?", ...).fetchall()
...
return f"{prefix}{max_number + 1:03d}"
```

Два параллельных запроса без `BEGIN IMMEDIATE` могут получить одинаковый ID. В `create_booking()` транзакция есть, но в `admin_client_add()` — нет. Оберните INSERT в `BEGIN IMMEDIATE` или используйте `AUTOINCREMENT`.
